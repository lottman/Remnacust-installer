# Скрипт и помощники одной версии

Подготовлено в исходниках; публикация нового выпуска ещё не выполнена.

Скачанный `installer.sh` содержит полный комплект Python/CJS-помощников, включая лицензии. Для локальных команд не требуется загружать помощники из Latest. Установка и обновление приложений по-прежнему требуют доступа к выбранному выпуску и его образам либо настроенному зеркалу.

Скрипт проверяет SHA-256 манифеста, собственного кода и каждого помощника до их использования. Из исходного checkout он читает соседний проверенный комплект; установленная команда может использовать проверенный кеш. Если кеш отсутствует, повреждён или принадлежит другой версии, применяется встроенный комплект. Старые файлы в `/usr/local/lib/remnacust-installer` не подмешиваются. Скопированный отдельно сырой скрипт из checkout без полного комплекта завершится с понятной ошибкой до операций с Docker и БД. Для отдельного файла скачивайте Release asset `installer.sh`.

Проверенные файлы сначала копируются в приватный рабочий каталог операции. Постоянные комплекты сохраняются отдельно в `/usr/local/lib/remnacust-installer/helpers/<SHA-256 манифеста>`. Повреждённый старый комплект сохраняется, а новая копия получает отдельный путь. Одновременная публикация одинакового комплекта допускает повторное использование только после проверки всех файлов. Файлы активных поколений автоматически не удаляются: на них могут ссылаться работающие агенты.

Команда `/usr/local/bin/remnacust` заменяется через временный файл в том же каталоге. Сервис обновлений и его отдельный worker запускаются из конкретного каталога своего комплекта. Проверка хешей гарантирует согласованность файлов с выбранным скриптом; она не заменяет доверие к источнику самого скачанного скрипта.

Выбор старой версии панели или ноды не понижает помощники текущего скрипта. Например, новое `restore-panel` использует актуальный план восстановления даже при старом архиве приложения. Проверка выпуска для обновления через панель экспортирует самостоятельный скрипт: для более нового установщика — скрипт и комплект этого выпуска, для старого приложения — текущий комплект. Полный архив исходников и небольшой runtime-архив также содержат самостоятельную точку входа. Это позволяет прежнему агенту передать новому скрипту полный комплект.

Восстановление сохраняет установленную версию панели и инфраструктуру, возвращая данные и ключ из копии. Ошибки миграции оставляют писателей остановленными с соответствующим восстановленной БД ключом. Согласование финансовых резервов после восстановления — отдельная процедура: совпадение файлов помощников не разрешает автоматически продолжить выдачу квот.

## Подготовка выпуска

После изменения `VERSION`, `installer/installer.sh`, любого файла из `helper_bundle.FILES`, `LICENSE` или `NOTICE.md` выполните из корня репозитория:

```bash
python3 installer/helper_bundle.py sync --root .
python3 installer/helper_bundle.py check --root .
bash tests/installer.test.sh
python3 tests/package-release.test.py
```

Зафиксируйте `installer/helper-contract.json` вместе со скриптом и помощниками до создания тега. Пакетировщики читают закреплённые исходники и отказываются выпускать несовпадающий комплект; CI не переписывает манифест для сокрытия рассогласования. Встроенный архив воспроизводим, повторная упаковка не вкладывает его в себя.

Проверки включают повреждённый/чужой комплект, работу без сети, повторную и параллельную установку, экспорт старого приложения и нового установщика, а также фактическое восстановление на одноразовом Docker/PostgreSQL-стенде. Последний проверяет оркестрацию установщика на небольшом тестовом образе; он не заменяет сквозную проверку всей панели и координатора резервов.
