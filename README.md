# Remnacust Installer

Установка и обслуживание панели и ноды Remnacust. Нода включает наш Xray: отдельной команды обновления ядра нет. Образы собираются в GitHub Actions. Сервер скачивает готовый образ из GHCR по закреплённому digest; при недоступном реестре используется копия того же образа из публичного Release. Версия, архитектура и идентификатор проверяются до изменения установки. Сборки на VPS нет. Токен файлового хоста или GitHub не требуется.

Обновление принимает оба формата `environment` в Compose: объект и список `KEY=VALUE`. Ошибки конфигурации показывают конкретную причину и записываются в журнал без вывода секретов.

При обновлении ноды `SECRET_KEY` и `NODE_PORT` берутся из её существующего контейнера. Если в старом Compose или `.env` остался другой порт, он не заменит рабочий API-порт. Остальные переменные и ссылки на них, исходные файлы и `.env` сохраняются; установщик записывает отдельный Compose-файл для обновлённой ноды.

## Быстрый запуск

Скопируйте всю строку в консоль сервера. Она скачает установщик и откроет меню:

```bash
curl -fsSL --proto '=https' --proto-redir '=https' https://github.com/lottman/Remnacust-installer/releases/latest/download/installer.sh -o installer.sh && sudo bash installer.sh
```

[Скачать installer.sh](https://github.com/lottman/Remnacust-installer/releases/latest/download/installer.sh). Для установки без меню добавьте в конец строки `install-panel` или `install-node`.

Для просмотра справки достаточно Bash: `bash installer.sh --help`. В меню установленный компонент получает действие «Удалить» вместо «Установить». Обновить отсутствующий компонент нельзя. Наличие установки проверяется по каталогу, Docker/Compose-файлу, записи установщика и контейнерам Compose; остановленные контейнеры тоже считаются установленными. Цвета отключаются через `NO_COLOR=1`; журнал операции хранится в `/opt/remnacust/logs` с доступом только для root.

Если репозиторий скачан целиком, файл находится в `installer/installer.sh`.

## Команды

| Команда | Действие |
| --- | --- |
| `install-panel` | Новая панель, PostgreSQL 18, Valkey, Caddy с HTTPS |
| `install-node` | Новая нода с нашим Xray; Nginx и TLS — при `--node-domain` |
| `upgrade-panel` | Обновление API, worker и scheduler с копией БД |
| `upgrade-node` | Обновление ноды вместе с Xray |
| `uninstall-panel`, `uninstall-node` | Удаление контейнеров с сохранением данных, томов и конфигурации |
| `migrate-remnawave-panel` | Замена образов существующей панели с сохранением её Compose-проекта |
| `migrate-remnawave-node` | Замена образа существующей ноды с сохранением ключа и портов |
| `migrate-marzban-panel` | Перенос пользователей из Marzban в установленную Remnacust |
| `--check-release` | Скачать и проверить выпуск без установки |
| `status`, `logs` | Состояние контейнеров, последние 100 строк журнала |
| `check-panel` | Проверка DNS и ответа панели по HTTPS без изменения конфигурации |
| `start`, `stop`, `restart` | Управление приложением; остановка не удаляет БД и тома |
| `backup-panel`, `restore-panel` | Копия БД и конфигурации / восстановление выбранной копии |
| `renew-node-certificate` | Проверка и копирование обновлённого сертификата; перезапуск ноды/Nginx |
| `renew-panel-certificate` | Проверка и копирование готового сертификата; reload Caddy без перезапуска панели |

При установке, обновлении и миграции запрашивается версия выпуска установщика. Enter выбирает `latest`; `--version 1.2.14` закрепляет выпуск. Установщик 1.2.14 содержит панель версии 1.1.6, ноду и ядро 1.1.1: версии компонентов закреплены в `component-sources.json` и проверяются отдельно. `--yes` пропускает подтверждение, но обязательные параметры и ключи всё равно нужны.

Вопросы подтверждения и настройки TLS/XHTTP ноды показывают только `y/n`: в цветном терминале `y` выделяется зелёным жирным, `n` — красным жирным. `y` подтверждает, `n` и Enter отменяют действие; в вопросе TLS Enter оставляет TLS выключенным. Регистр и пробелы по краям не важны. Незнакомый ответ повторяет вопрос на месте. При `NO_COLOR`, `TERM=dumb` или выводе в файл управляющие коды цвета не печатаются.

В меню вводите номер действия. Пустая или неверная строка повторяет только вопрос, а не всё меню. Остаток вставленного текста удаляется из буфера терминала после ошибки ввода и возврата из действия, чтобы старые логи не вызывали новые команды. Для автоматизации используйте явную команду с параметрами и `--yes`, а не несколько ответов, вставленных в интерактивное меню. Закрытие ввода или Ctrl+D завершает ожидание без повторяющегося вывода.

После успешной установки, обновления или миграции панели/ноды выводится отдельный итоговый блок и скрипт завершается с кодом `0`. В нём выделены адрес входа, порядок создания администратора или прежняя авторизация, API-порт ноды, путь к `.env`, команды проверки и журналы. Для предоставленного сертификата показаны исходные пути сертификата и ключа, пути рабочих копий и команда продления; содержимое ключей и пароли не печатаются. Автоматический сертификат обслуживает Caddy, а при `--proxy existing` путь сертификата определяется конфигурацией вашего Nginx/Caddy.

Отмена, ошибка и команды обслуживания возвращают вас в меню. Можно исправить домен и повторить установку, не скачивая скрипт заново. При запуске конкретной команды, например `bash installer.sh install-panel --yes ...`, ошибка возвращает ненулевой код для автоматизации и не открывает меню.

```bash
sudo bash installer.sh install-panel --domain panel.example.com --email admin@example.com --version latest
sudo remnacust upgrade-panel --version 1.2.14
sudo remnacust status --component node
sudo remnacust backup-panel
sudo remnacust restore-panel --backup /opt/remnacust/backups/panel-DATE-ID
```

## Новая установка

Установка, обновление и миграция поддерживаются только на Ubuntu 22.04 LTS, Ubuntu 24.04 LTS и Ubuntu 26.04 LTS, amd64 и arm64. На другой ОС установщик завершается до установки пакетов и изменения приложения. Проверка выпуска, справка и обслуживание ранее установленного приложения не ограничены этими версиями ОС. При выборе старого выпуска установленная команда `remnacust` сохраняет проверку ОС текущего установщика.

Нужны root, доступ к GitHub, Docker Hub и репозиториям пакетов. Для работы панели нужны минимум 2 CPU, 2 GiB RAM и 20 GiB диска; рекомендуются 4 CPU и 4 GiB RAM. Для ноды — минимум 1 CPU и 1 GiB RAM, с запасом под нагрузку Xray. Node.js, npm и Go на VPS не нужны. Перед скачиванием проверяется запас диска для образа; исходники и инструменты сборки остаются в GitHub Actions. [Требования Remnawave](https://docs.rw/install/requirements/) используются для планирования ресурсов; список ОС установщика Remnacust ограничен тремя версиями Ubuntu LTS.

Установщик добавляет Docker только при его отсутствии. Если установлен Docker без Compose v2, добавляется только пакет Compose. Существующий daemon не переустанавливается. SSH, системные sysctl и посторонние службы не перенастраиваются.

Панель получает случайные `APP_SECRET`, пароль PostgreSQL, пароль метрик и секрет webhook. HWID включён по умолчанию для новой установки. Backend публикуется только на `127.0.0.1`, БД и кеш не имеют публичных портов. Перед установкой запрашиваются домен, reverse proxy и способ получения сертификата. Для автоматического HTTPS также нужна почта ACME. Backend панели с новым Caddy должен использовать другой порт (по умолчанию 3000). Caddy обслуживает домен на 80/443; A/AAAA должны указывать на сервер, оба порта должны быть доступны. При `--proxy existing` HTTPS настраивается вашим reverse proxy. После запуска создайте администратора в панели.

Caddy работает в Docker, поэтому `systemctl status nginx` на новой установке панели возвращает «Unit could not be found». Проверяйте `sudo remnacust status --component panel` и `sudo remnacust logs --component panel`: там видны приложение и Caddy. При миграции установщик сохраняет прежний Caddy или Nginx, его образ, конфигурацию, сертификаты и порты; новый прокси не устанавливается.

Перед скачиванием Docker-образа для автоматического сертификата установщик запрашивает публичные A и AAAA через Google DNS, с Cloudflare DNS в качестве резервного сервиса. Каждая опубликованная запись должна вести на этот сервер. Учитываются публичные IP сетевых интерфейсов и внешний IPv4/IPv6 через ipify. Если запись неверна, отсутствует или проверка недоступна, контейнеры не создаются. Исправьте DNS, дождитесь обновления записей и повторите действие. Для NAT с другим входящим адресом укажите `--server-ip IPv4[,IPv6]`. Проверка также применяется к HTTP-01 новой ноды; DNS-сертификаты и собственный reverse proxy могут использовать другой внешний адрес.

После запуска установщик ждёт HTTPS до трёх минут, проверяя доверие сертификату и ответ `/api/auth/status`. Если HTTPS не подтверждён, он показывает причину запроса, сохраняет журнал Caddy и возвращает вас в меню. Команды обслуживания, контейнеры и данные уже запущенной панели остаются доступными. Исправьте DNS или доступ к 80/443 и проверьте её снова; переустановка не нужна:

```bash
sudo bash installer.sh check-panel
# Если домен не записан в метаданных старой установки:
sudo bash installer.sh check-panel --domain panel.example.com
```

Используйте свежескачанный `installer.sh`, если установленная команда `remnacust` ещё старой версии. `check-panel` читает состояние и делает сетевые запросы; контейнеры, proxy, БД и сертификаты не перезапускает. Если само приложение остановлено, сначала проверьте журнал и выполните `sudo remnacust start --component panel`. Повторная установка поверх созданных файлов блокируется, чтобы сохранить секреты и данные.

Нода требует `SECRET_KEY` из этой панели — это пакет сертификатов для её авторизации, а не дополнительный токен скачивания. Ключ вводится скрыто. Для автоматизации передайте его через защищённое окружение `REMNACUST_NODE_SECRET`; не записывайте в историю команд. Формат, подпись, приватный ключ и срок сертификата проверяются до запуска.

```bash
sudo bash installer.sh install-node --port 2222 --panel-ip 203.0.113.10
sudo bash installer.sh install-node --port 2222 \
  --node-domain edge.example.com --email admin@example.com
```

`--panel-ip` добавляет правила доступа к API только в уже активный UFW. Установщик не включает и не сбрасывает firewall. Если UFW не активен, ограничьте порт API адресом панели в firewall провайдера. Укажите этот же порт при добавлении ноды в панели. Xray начнёт обслуживать пользователей после назначения профиля.

### Сертификат и почта

При новой установке с HTTPS доступны четыре варианта:

| Вариант | Что потребуется | Продление |
| --- | --- | --- |
| Автоматический Caddy для панели / HTTP-01 для ноды | Домен и email ACME; доступный TCP 80 | Caddy автоматически; для ноды — отдельный systemd timer |
| Cloudflare DNS | Email ACME и API token с правом DNS Edit нужной зоны | Certbot и отдельный systemd timer |
| Gcore DNS | Email ACME и API token с правом изменения DNS нужной зоны | Certbot и отдельный systemd timer |
| Готовый сертификат | Пути к fullchain.pem и privkey.pem | Продлевается прежним способом; затем команда renew-panel-certificate / renew-node-certificate |

Email и токен DNS — разные данные. В меню токен вводится скрыто; в автоматизации используйте `--dns-credentials` с INI-файлом и правами `600`. Установщик сохраняет копию в закрытом каталоге `/opt/remnacust/acme/PROJECT`, чтобы продление не зависело от временного файла. GitHub-токен для скачивания не нужен.

```bash
# Автоматический HTTPS панели
sudo bash installer.sh install-panel --domain panel.example.com --email admin@example.com --yes

# Сертификат через Cloudflare DNS
sudo bash installer.sh install-panel --domain panel.example.com \
  --tls-method cloudflare --email admin@example.com --dns-credentials /root/cloudflare.ini

# Уже есть подходящий сертификат
sudo bash installer.sh install-panel --domain panel.example.com --tls-method existing \
  --cert-file /etc/letsencrypt/live/panel.example.com/fullchain.pem \
  --key-file /etc/letsencrypt/live/panel.example.com/privkey.pem

# Панель за своим действующим reverse proxy
sudo bash installer.sh install-panel --domain panel.example.com --proxy existing
```

Содержимое `/root/cloudflare.ini`:

```ini
dns_cloudflare_api_token = YOUR_TOKEN
```

Для Gcore используйте `--tls-method gcore` и поле `dns_gcore_apitoken` в INI. `chmod 600 /root/cloudflare.ini` закрывает доступ другим пользователям. DNS-метод не требует HTTP-01 на порту 80, но новый Caddy всё равно занимает 80/443 для панели. Wildcard-сертификат можно подключить как готовый файл, если он покрывает указанный домен; hostname панели и ноды должен быть конкретным.

Готовая пара проверяется до создания установки: домен, срок действия с запасом минимум сутки, формат PEM и соответствие приватного ключа. RSA и ECDSA поддерживаются. Сертификат копируется в `certs` с правами `600`; после обновления исходных файлов выполните `sudo remnacust renew-panel-certificate` или `sudo remnacust renew-node-certificate`. Для доверия клиентов сертификат должен быть выдан доверенным центром и содержать полную цепочку.

Caddy сам получает и продлевает автоматический сертификат. Для HTTP/DNS Certbot находится в отдельной Python venv с закреплёнными версиями; системный Python не изменяется, пакеты берутся готовыми wheel. У каждой установки собственные ACME-файлы и таймер `remnacust-acme-PROJECT.timer`. Deploy-hook копирует только её сертификат: на панели вызывает Caddy reload, на ноде перезапускает Nginx и Xray. Таймеры, SSH и firewall посторонних приложений не перенастраиваются.

При `--proxy existing` установщик не управляет сертификатом. При upgrade/migrate мастер TLS не запускается: Nginx/Caddy, сертификаты, почта ACME, сети и порты сохраняются. Параметры создания нового TLS с этими командами отклоняются до изменений.

### Если предыдущая установка осталась на сервере

Работающие и остановленные контейнеры учитываются до запроса версии, подтверждения и домена. Если записи установщика нет, но проект Compose остался, повторный `install-panel` завершается с указанием существующего проекта/каталога. Не удаляйте каталог и тома ради повторной установки: это не обновление.

```bash
sudo bash installer.sh upgrade-panel --directory /opt/remnacust/panel
# Если панель установлена в другом месте, укажите её реальный каталог или контейнер:
sudo bash installer.sh upgrade-panel --container YOUR_PANEL_CONTAINER
# Для существующего Remnawave:
sudo bash installer.sh migrate-remnawave-panel --directory /opt/remnawave
```

Если осталась только БД/инфраструктура без контейнера панели, меню всё равно предлагает удалить собственный проект с сохранением томов. После удаления доступна только новая установка, даже если Compose сохранился. При недоступном Docker daemon установщик просит восстановить доступ к Docker и не считает сервер пустым. Проверка повторяется после получения блокировки, чтобы параллельный запуск не создал вторую установку.

### TLS и XHTTP

`--node-domain` включает настройку TLS и Nginx. В интерактивном режиме установщик сам предлагает её; без TLS достаточно SECRET_KEY и API-порта. Способы получения сертификата одинаковы с панелью, кроме автоматического Caddy: на ноде вместо него используется Certbot HTTP-01. DNS должен быть настроен, а для HTTP-01 порт 80 должен быть свободен и доступен извне. API-порт ноды должен отличаться от 80 для этого способа, иначе продление станет невозможным. В меню запрашиваются также API-порт и адрес панели для ограничения доступа. Сертификаты хранятся в `certs`, общий каталог сокетов — в `run`. Nginx принимает TLS с PROXY protocol на `/var/lib/remnacust/run/nginx.sock`; путь `/xhttppath/` направлен на `/var/lib/remnacust/run/xhttp.sock`. После продления сертификата deploy-hook копирует его и перезапускает Nginx и ноду.

Настройте в профиле Xray Unix inbound XHTTP: `listen` = `/var/lib/remnacust/run/xhttp.sock,0666`, `path` = `/xhttppath/`. Суффикс `0666` нужен для доступа worker Nginx к сокету. Для fallback на Nginx задайте `dest` = `/var/lib/remnacust/run/nginx.sock` и `xver: 1`. Сертификат и ключ доступны в `/var/lib/remnacust/tls/fullchain.pem` и `/var/lib/remnacust/tls/privkey.pem`. Публичный listener 443 принадлежит Xray. Профили панели автоматически не переписываются. Для REALITY без собственного TLS-сайта `--node-domain` не нужен.

## Миграция и обновление

```bash
sudo bash installer.sh migrate-remnawave-panel --container remnawave
sudo bash installer.sh migrate-remnawave-node --container remnanode
```

Можно указать `--directory /opt/remnawave` или `--compose-file /opt/remnawave/docker-compose.yml`. При нескольких установках используйте точное имя контейнера. Сохраняются имя Compose-проекта, сети, тома, образы БД/кеша, `.env`, порты и ключи. PostgreSQL 17 не заменяется на 18 во время миграции. Новая управляемая Compose-конфигурация создаётся рядом с исходной; исходные файлы остаются в резервной копии.

Требуется Compose v2 и исходный `APP_SECRET` панели либо `SECRET_KEY` ноды. Старую панель без `APP_SECRET` сначала обновите по официальному пути Remnawave. Отсутствующий секрет не заменяется случайным. Неизвестная, незавершённая или изменённая миграция БД останавливает перенос до выключения приложения. Установки с несколькими сетями приложения требуют предварительного выбора одной однозначной сети. Для внешней БД с дополнительными SSL-файлами заранее проверьте доступ резервного копирования; автоматический перенос нестандартных SSL-mounts не предусмотрен.

Готовый образ скачивается и проверяется до остановки приложения. Затем создаются копии БД и Compose; после остановки всех обнаруженных процессов делается окончательный dump. БД и кеш продолжают работать. Отдельные API/processor/scheduler обновляются вместе; ранее отключённые процессы не запускаются. Приложения вне этого Compose-проекта, подключённые к той же БД, нужно остановить отдельно.

Проверяются исходные учётные записи, ключи пользователей, профили и настройки. Старая сборка с переименованными таблицами и `xera1`-паролями исправляется встроенной процедурой совместимости, используя исходный `APP_SECRET`.

При неудаче обновления ноды запускается предыдущая конфигурация. Если панель уже начала менять БД, её процессы останавливаются и выводится команда восстановления. База автоматически не затирается. `restore-panel` проверяет суммы копии, сохраняет текущую БД и восстанавливает выбранный dump одной транзакцией. Автоматическое восстановление рассчитано на выделенную базу панели с пользовательской схемой `public`; дополнительные пользовательские схемы требуют ручного восстановления. Схема заменяется внутри транзакции, поэтому старые и переименованные таблицы не конфликтуют. Храните каталог установки и образы предыдущего выпуска до завершения проверки обновления. Копии содержат секреты; права каталога — 700, файлов — 600.

`backup-panel` сохраняет фактическое состояние процессов. При восстановлении ранее выключенные worker/scheduler остаются выключенными; копия полностью остановленной панели не запускает её автоматически. Для старых копий без списка процессов используется прежний режим запуска всех приложений. Контрольные суммы больших dump вычисляются потоком, без загрузки всей базы в память; конфигурация и файлы окружения также проверяются перед восстановлением.

## Перенос Marzban

Сначала установите Remnacust, подготовьте профили/хосты/ноды и внутренний сквад. Создайте API token с правами чтения пользователей и сквадов, создания пользователей. Это обычная авторизация API; установке она не нужна. У Marzban используйте администратора, который видит всех нужных пользователей.

```bash
sudo bash installer.sh migrate-marzban-panel \
  --source-url https://marzban.example.com \
  --destination-url https://panel.example.com \
  --internal-squad aaaaaaaa-aaaa-4aaa-aaaa-aaaaaaaaaaaa \
  --dry-run
```

Пароль Marzban и API token вводятся скрыто; для автоматизации доступны `MARZBAN_USERNAME`, `MARZBAN_PASSWORD`, `REMNACUST_API_TOKEN`. Удалённые API требуют HTTPS. HTTP допускается только на localhost, например через SSH-туннель. Redirect отклоняется, чтобы ключ не попал на другой адрес.

Команда сохраняет полный экспорт, план и отчёт в закрытом каталоге `/opt/remnacust/backups/marzban-*`. `--dry-run` не создаёт пользователей. После проверки отчёта повторите команду без этого флага. При конфликтах предварительная проверка останавливает весь импорт. Совпадающие записи пропускаются; отличающиеся не перезаписываются. После каждого создания проверяются ключи и назначение сквада. Частичный сбой возвращает ненулевой код и оставляет отчёт для повторного запуска. На время окончательного переноса остановите редактирование пользователей и обновление их квот в Marzban: API не предоставляет транзакционный снимок всей базы. Исходная панель и её пользователи этой командой не изменяются.

Переносятся VLESS UUID, Trojan/SS-пароли, сроки, дата создания, заметка и статус. Имена и пароли, не проходящие валидацию новой панели, не переименовываются и не генерируются заново. VMess и другие неподдержанные этим импортом протоколы требуют отдельной подготовки. `on_hold` становится `DISABLED`: срок активации по первому подключению автоматически не переносится. Бессрочный срок задаётся до 31.12.2099, годовой сброс — `NO_RESET`.

Счётчик потраченного трафика не поддерживается API создания пользователя. По умолчанию `--quota-mode remaining` переносит остаток квоты с `NO_RESET`; будущие продления настройте отдельно. Исчерпанная квота остаётся заблокированной. `--quota-mode total` сохраняет полную квоту и период сброса, но счётчик начинает с нуля, поэтому может повторно выдать уже потраченный трафик. Оба режима сохраняют исходные значения в экспорте.

`--preserve-subhash` сохраняет совместимый короткий токен. JWT-ссылки Marzban требуют отдельной subscription-page: `MARZBAN_LEGACY_LINK_ENABLED`, исходного `MARZBAN_LEGACY_SECRET_KEY`, API token и старого префикса. Смена DNS/proxy и установка legacy-page не выполняются этой командой. Проверьте старую ссылку и реальное подключение перед отключением Marzban. Администраторы, серверные конфиги, inbound-привязки и история трафика этой командой не импортируются.

## Удаление и повторная установка

`sudo remnacust uninstall-panel` и `sudo remnacust uninstall-node` находят работающие и остановленные контейнеры даже без записи установщика, Compose-файла или прежнего каталога. Удаление работает без скачивания выпуска и без `docker compose`. Перед подтверждением выводится список контейнеров. Если установок несколько, выберите нужную через `--container`, `--directory` или `--project-name`.

Удаляются контейнеры приложения и принадлежащая установщику инфраструктура. Тома, `.env`, сертификаты и резервные копии сохраняются. На перенесённой панели общий Caddy/Nginx, БД и сторонние сервисы остаются на месте. До удаления сохраняется описание выбранных контейнеров в `/opt/remnacust/backups/uninstall-COMPONENT-DATE-ID`: каталог имеет права `700`, файлы — `600`, поскольку могут содержать секреты. После удаления установщик проверяет, что выбранные контейнеры действительно исчезли; при ошибке Docker операция не отмечается как успешная.

После удаления меню предлагает `install-panel` или `install-node`. Это действует и для старых записей с `recoverable=true`, и при сохранённом Compose. Команды `start`, `restart` и `restore-panel` для удалённой установки отклоняются с указанием команды новой установки. Перед заменой записи установщик сохраняет её в `backups/reinstall-COMPONENT-DATE-ID/registry.json`.

Повторная установка получает отдельный каталог и проект Docker, новую пустую БД и новые ключи. Прежние тома, файлы и сертификаты сохраняются и автоматически не подключаются. Установщик проверяет тома даже при отсутствии записи установки, чтобы случайно не подключить старую БД к новой панели с другим паролем. Явный `--project-name` с уже существующими томами отклоняется. Обычные команды запуска и восстановления резервной копии остаются доступны для текущей, не удалённой установки.
